**Ruling 11 — Ruling 9's sanitiser is incomplete and must also reject embedded tab, CR and LF. Amends Ruling 9.**
The reviewer found a live bypass in the fix I issued mid-task, and verified it by reproducing the function bodies: `_safe_next("/\t/evil.example")` returns the string unchanged, because it starts with a single `/` and not with `//` or `/\`. Per the WHATWG URL Standard, the basic URL parser removes ASCII tab, LF and CR from the input **wherever they occur** — not only at the edges, unlike other control characters, which are merely trimmed from the ends. So the browser silently strips that tab at parse time, turning the value into `//evil.example`, a protocol-relative URL, and navigates off-origin immediately after a cookie-setting login. The server and client guards "agreed" only in the sense that they shared the identical flaw, so neither backstopped the other, and none of the five tests I specified covered the vector — the suite reported green over a live bypass.
Ruling: reject any value containing `\t`, `\r` or `\n` outright, before the prefix checks, applied identically on both sides, with regression tests for all three characters. Rejecting beats strip-and-recheck: stripping invites ordering subtleties, and no legitimate redirect path contains those bytes.
*Cost if wrong:* a redirect target containing a literal tab or newline is refused and the user lands on `/` — which is not a real use case.

**Ruling 12 — the locked-account branch must verify a hash before returning, for timing uniformity.**

**Ruling 6 — SQL equality on a stored digest satisfies the token-handling constraint; `hmac.compare_digest` binds in-process comparison only.**
Task 3's implementer flagged that `load_session` and `redeem_user_token` find rows with `WHERE token_hash = %s` rather than `hmac.compare_digest`, which my Global Constraints list appeared to require for all token comparison. The constraint as I wrote it was over-broad. What is compared in SQL is already a SHA-256 digest, not the secret; an indexed lookup cannot be made constant-time without degrading to a full table scan of every session row; and a timing leak of the *digest* buys an attacker nothing, because producing a token the server accepts would require inverting SHA-256. `hmac.compare_digest` genuinely binds the password path, where one row is fetched and compared in process — and Task 1 does exactly that.
So: the code stands, and the constraint text handed to reviewers from Task 3 onward is narrowed to say this explicitly, so it is not re-raised on every remaining task.
